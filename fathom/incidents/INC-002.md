## What happened

Found during the first full failure-drill run. Every `edp run` began with
`alter table raw.load_runs add column if not exists ...`. Even when the column
exists, that statement asks for an exclusive lock on the table. The drill
harness had read `raw.load_runs` in a transaction it had not closed, so the
run waited for that reader, and the reader was waiting for the run. Nothing
timed out. The run hung for ten minutes until it was killed by hand.

In production the reader would be an analyst's SQL client or a dashboard left
open in a transaction. The schedule would stop with no error and no alert,
and the only signal would be the freshness monitor two hours later.

## Fix

- `ensure_schema` checks `information_schema` and only alters a table when a
  column is actually missing, so a normal run takes no exclusive lock.
- The drill harness reads in autocommit mode.
- The pipeline's session sets `lock_timeout = 30s`, so any future lock wait
  fails in seconds with a clear error, which the monitors then report.
