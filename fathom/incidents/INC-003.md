## What happened

A planned drill (`python -m edp.drills`). The Odoo server was stopped. The
next `edp run` retried the connection with backoff, then failed in 6.2
seconds with `OdooUnavailable ... Connection refused`, exit code 1. The run is
recorded as failed in `raw.load_runs`, and the `last_run` monitor reported it.
The finance tables were left as they were, so nobody read half-loaded data.

While Odoo was down, the business kept working: 3 deals, 3 invoices and 2
payments were entered once it came back. The next run loaded 26 new record
versions in 4.6 seconds, and the totals matched Odoo again.

## What it showed

Recovery needs no manual step: the watermark only moves when a load succeeds,
so the next run picks up everything that changed. The gap a person would see
is staleness, which is why the freshness rule CON-103 exists.
